# 0 落盘上传：本仓库视角的可行性与省空间幅度

> 只读调研结论。没有改业务代码，没有部署，没有碰节点、录制或上传进程，也没有发起真实上传。
> 基线：`feat/hub-optimization` @ `077d129`。本文只讨论本仓库与 B 站上传协议本身，
> 不引用任何第三方项目。

## 结论

**对空间有帮助，但省的是「峰值占用」和「留存时长」，不是「峰值归零」。**

分三档说清上限：

- 严格 0 落盘（一个字节都不落）：**做不到**。UPOS 协议要求上传前先声明分 P 的总大小，
  而直播流长度事先未知；异常路径（网络落后、断流、提前结束）没有本地字节可重传。
- 小窗口落盘：可做。磁盘占用从「整场录像」降到「一个上传窗口 + 一段兜底」。
- 延长分 P、不提提交频率：保守基线。空间占用上升，但提交次数下降，不撞限流。

具体能省多少，取决于**分 P 大小**和**上传是否跟得上录制**，见下面的量化。

## 为什么做不到严格 0 落盘

协议侧的硬约束（B 站 UPOS 上传）：

1. preupload 请求必须带 `size`（分 P 预期总长度）。拿不到这个值就拿不到上传地址。
2. chunk 数 `chunks = ceil(total / chunk_size)` 在**第一个 chunk 发出前**就已确定。
3. 每个 chunk 的参数 `total` / `size` / `start` / `end` / `partNumber` 都由总大小和
   chunk 索引预先算出，不能「边产生边无限追加」。
4. complete 之前会校验 parts 连续（1..N），中间不能有洞。

因此流式上传只能选一个固定的「每 P 大小」，到点截断并 complete，再开下一个 P。截断点必须
落在容器可解析的位置，不能靠补字节凑长度。

异常路径是第二道坎：网络跟不上时纯管道没有已落盘字节可以重传；直播流不可重放。要么保留
一小段缓冲，要么接受「这一段丢了，人工处理」。任何一种都不再是严格 0 落盘。

## 本仓库现状

### 录制端只写文件

- `packages/record-engine/src/engines/ffmpeg` 的 `buildFfmpegArgs` 输出目标始终是磁盘路径
  （分段模板或单文件 TS）；`spawn` 把 stdout 设为 `ignore`，只从 stderr 解析分段打开事件
  和 `time=`，没有媒体管道。
- `packages/record-engine/src/engines/mesio` 同样给输出目录与文件名模板，产物落在磁盘上。
- `packages/record-engine/src/index` 的 `spawnRecording` 把 `dir` / `nameBase` / `segSec`
  交给引擎，分段路径经 `onSegment` 回调交给 manager。

所以第一道改动在录制引擎：需要新增「stdout 媒体流」模式，并重做分段、进度、卡死看门狗、
断流重连、收尾语义。现有引擎契约里没有这个位置。

### 边录边传以「已封口文件」为单位

- `packages/core/src/rolling` 的五条不变量：只处理已封口分段；确认后才删源；弹幕文件不删；
  不销毁唯一副本；低水位只拒新开录。
- 同文件的封口判定依赖分段文件和「出现后继段」这两个文件级信号；正在写的文件永不上传。
- 删源要求「封口 + 上传确认 + 房间身份一致」三重证据齐备。
- `packages/app/src/rolling-upload` 的执行体：封口后才进入上传，失败或结果不确定时保留源
  并做头阻塞；崩溃恢复依赖 sidecar 里的上传意图和稿件分 P 数查询。

结论：流式上传不能塞进现有 `RollingUploader`。它现在的前提是「源文件存在且已封口」，
流式需要另一套以「分 P 边界 + 上传确认」为准的状态机。

### 节点侧整场管线同样以文件为输入

- `packages/app/src/node-pipeline` 的 `produceParts` 先 remux / merge / 硬链接出成品文件，
  再交给上传。
- 上传前用 ffprobe 自检，读不出时长的分 P 直接拒投（B 站会先收下，再在转码阶段暴露失败）。
- 落「上传中」标记 → 建稿 → 逐个 append，每次 append 前写意图；建稿后失败记 failed，
  无稿件标识的失败保持「上传中」表示结果不确定。
- 上传成功后才清源；弹幕文件一律保留。

流式上传会绕开这层「完整文件自检」，需要等价的边写边校验，否则坏分 P 的风险更高。

## 对空间的实际影响

### 现状占用模型

节点侧的峰值大致是：`源分段（整场）` + `stage 成品 + 中间产物` + `rolling 未确认段`。

边录边传已经解决的是**留存时长**：确认过的段立刻删掉，所以稳态占用 ≈ 一个分 P 周期内的字节，
而不是整场长度。剩下的占用是「分 P 大小」决定的窗口。

### 三种形态的空间对比

设码率 R、单场时长 T、分 P 时长 S：

| 形态 | 峰值磁盘占用（视频部分） | 提交次数 | 失败可重传 |
|---|---|---|---|
| 现状：不边录边传 | R × T（整场） | 1 | 有 |
| 现状：边录边传 + 窗口 S | 约 R × S（确认即删） | 约 T / S | 有（保留未确认段） |
| 延长分 P 到 S'（S' > S） | 约 R × S' | 约 T / S' | 有，但单段重传代价更大 |
| 小窗口 spool（流式 + 兜底） | 约 R × S + 兜底余量 | 约 T / S | 有（窗口内保留） |

结论：

- **边录边传本身已经省掉了整场这一项**，剩下的空间就是「窗口」大小，由分 P 时长决定。
- 要继续省，只能压窗口：缩短分 P，或者上小窗口 spool。但缩短分 P 会**提高提交频率**，
  正是当前撞限流的方向（见下）。所以空间和提交频率是同一个旋钮的两端。
- 兜底缓冲（tmpfs 或临时目录）也要计入预算，且必须与录制侧的剩余空间检查一致；
  否则「省下来的盘」会被缓冲占回去。

### 和提交频率的关系

当前 120 秒分段的实测：前 4 段成功，第 5 段被 B 站以「请求过于频繁」拒绝。这说明瓶颈是
**提交/请求频率**，不是网络吞吐，也不是磁盘写不下。

- 缩短分 P → 提交更密 → 更频繁撞上限，空间省了但成功率下降。
- 延长分 P → 提交更稀 → 撞限流概率下降，空间占用上升。
- 0 落盘不改变提交次数。若仍每 120 秒提交一次，不写磁盘只会让请求来得更连续、更稳定地
  撞上限。

所以对空间有帮助的组合是：**延长分 P（或合并多个小段再提交）+ 流式/短窗口落盘**，
而不是单纯追求更小的窗口。

## 方案对比

| 方案 | 严格 0 落盘 | 省空间 | 可行性 | 主要问题 |
|---|---|---|---|---|
| 纯管道（媒体流直接进上传） | 理论是 | 最大 | **不可行** | 上传端只接文件路径；协议需预声明大小；异常无源可重传 |
| 小窗口 spool + 封口后上传 | 否 | 大（占用 ≈ 一个窗口） | **最现实** | 需容量预算与清理；失败保留窗口内数据 |
| 延长分 P，不改落盘方式 | 否 | 反向（占用上升） | **保守基线** | 单 P 更大，失败重传代价更高；但直接降低提交频率 |
| 保持现状 + 缩短分 P | 否 | 小 | **不建议** | 提交更密，更容易撞限流；已被实测证伪 |

## 最小 PoC（不改业务代码、不真实上传）

目标：验证「固定大小 P + 预声明上传 + 顺序提交」在协议层成立，并量化窗口与兜底代价。

1. **离线合成流**
   - 用本地生成的测试媒体或本地 HTTP 流，ffmpeg remux 到 stdout。
   - 按固定字节或时长切成测试 P；不接真实直播。

2. **假上传端**
   - 记录每次 preupload 的 `size`、chunk 数、每块参数、complete 的 parts。
   - 断言：chunk 数与预声明大小一致；parts 连续；顺序与输入一致。

3. **异常路径**
   - 模拟流提前结束、消费者变慢、进程被杀。
   - 断言：不靠补字节凑长度；失败时窗口数据可保留或明确标记不可恢复；不重复提交。

4. **本地假接口端到端**
   - 用本地假 B 站接口跑「声明 → 分块 → 合并 → 提交」完整流程。
   - 不接真实账号，不产生真实稿件。

5. **准入标准**
   - 通过：参数正确、顺序正确、短流不伪造媒体、失败可判定且不重复提交、内存有上限。
   - 不通过：需要未知总大小、需要补字节才能合并、失败无法证明未提交。

## 明确不做 / 待决策

- 不把「上传端接管道」当成现成能力。
- 不把临时缓冲兜底宣传成严格 0 落盘。
- 不在没有识别「请求过于频繁」类限流码并做冷却前，提高提交频率。
- 不在没有等价媒体完整性校验的情况下上线纯流式上传。
- 真实上传仍需人工授权。

## 建议

1. **短期**：保持现有「封口后上传」，优先识别并冷却新增的限流码，同时评估延长分 P 或把多个
   小段合并成一次提交；这一步直接改善成功率，空间占用会略升。
2. **中期**：做小窗口 spool，把节点视频占用从「整场」压到「一个窗口 + 兜底」，并把窗口与
   兜底一起纳入空间预算与水位闸门。
3. **长期**：只有在固定 P 协议、断流续稿、失败可判定、媒体自检都通过后，才考虑纯内存
   环形缓冲 + 自研流式上传；到那一步也应保留一个可配置的兜底窗口。

**一句话**：0 落盘对空间有帮助，但真正决定占用的是「窗口大小」；纯管道做不到，
小窗口 spool + 延长分 P 是同时省空间和降提交频率的组合。
