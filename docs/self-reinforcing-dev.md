# 自强化循环开发（Self-Reinforcing Development）

> 状态：设计定稿，2026-10-12 起作为 issue 流转的全流程门禁。
> 提案：GitHub issue [#4](https://github.com/fuyucn/douyin-rec/issues/4)。
> 一句话：不是「学习」——学习只是积累经验；「自强化循环开发」要求**每一轮闭环都产出可执行的
> 改进（代码 / 回归测试 / 规则 / 指标）并立即进入下一轮**，让系统行为随轮次变好。

## 1. 五环闭环

```
 ① 观察 ──► ② 决策 ──► ③ 开发 ──► ④ 发布+验证 ──► ⑤ 回写强化
   ▲                                              │
   └────────────── 下一轮（复用沉淀）──────────────┘
```

### 环 1：观察（Audit）

- 值班 Audit 自动巡检三节点：录制状态、`sync_jobs` 台账、磁盘、queue、日志。
- 只读：不改代码、不删文件、不重启、不另开上传。
- **门禁：无证据不开。** 开 `incident` / `enhancement` 必须带命令输出、节点角色、查询时间。
- 用「当天第几场 / 节点角色」指代，隐私（主播名、房间号、key、BV、IP、路径）一律不进 issue。
- 频率：日常按 heartbeat；重大事件可要求立即跑一次。

### 环 2：决策（Triage）

- 打 `accept` / `decline` / `needs-decision`，`decline` 必须写原因。
- 危险类（上传、删源、删稿、部署、改 hub 规则、清理录像）**一律 `needs-decision`，等人拍板**，
  评论写「决定三行」：要决定什么 / 不做会怎样 / 建议选项。
- **自动 triage（2026-10-12 起）**：低风险 + 证据充分 + 可测试 → 自动 `accept`；
  证据不足 / 明确不做 → 自动 `decline`（写原因）；危险类或拿不准 → `needs-decision`。
  不是每张票都等人拍板，只有危险类才拦。
- **门禁：`needs-decision` 缺一行不算准备好；危险类永不自动 `accept`；拿不准就 `needs-decision`，不猜。**
- `accept` 后同步到 `TODO.md` 记 `T-N` 并链 issue，成为真正的开发契约。

### 环 3：开发（实现）

- **自动实现（2026-10-12 起）**：实现 heartbeat 扫到 `accept` 且无 `in-progress` 的票即认领，
  打 `in-progress` 并评论「哪个 agent、何时开始、范围、模型」；并行最多 2 张且改动范围不重叠。不再需要人点名派活。
- 一个 `accept` issue 一个分支，PR 写 `Fixes #N`（分步实现的票中间各步写 `Part of #N`）；实现会话**只开 PR，不合并**（合并归 review 会话）、
  不部署、不顺手做无关改动。
- 行为变更必须有回归测试钉住（无法自动化的，写明人工验证步骤）。
- 自审循环照旧：实现 → 自审找缺陷 → 修复 → 复审；`pnpm test` / `typecheck` / `bundle` 全绿。
- issue 评论也算输入：可以不采纳，但 PR 里必须写理由。
- **合并 PR 由 review agent 做（2026-10-12 起）**：实现会话只开 PR，不合并；独立 review 会话按
  「review 门禁」审查，**通过即 `gh pr merge --merge` 自动合并**，不等人操作。**部署永远是人做**。
- **close 由实现 agent 做**（2026-10-12 起）：过完「四不 close」四条门禁就 `gh issue close` 并写明依据；
  缺任一条就留 open 并写清缺口。注意 PR 的 base 是 `feat/hub-optimization` 而非默认分支 `main`，
  `Fixes #N` 不会自动关票，close 必须显式执行。

### 环 4：发布 + 验证（Release & Verify）

- 部署 guard 不变：master 与任一 worker `recording===true` 就等；用户明确 override 除外。
- 部署完成后**核对版本**，然后**尽量实跑一场**走真实链路（录 / 传 / 删源），
  以台账终态 + 文件系统状态为证据，不凭日志印象下结论。
- **门禁：验证达标才算完成；没开播或时间不够要如实留作待办，不伪造结论。**
- 修复类 issue 的验证重点是「缺陷不再复现」：例如实测泄漏场景先留对照，
  部署后确认新链路能收口并删源，再清对照。

### 环 5：回写强化（Reinforce）

- 每轮闭环必须回写**至少一项**可复用资产（可多项）：
  1. **回归测试**：把这次根因写成自动化用例，同类错误当场红。
  2. **规则/设计沉淀**：更新设计文档或工作流，把「踩过的坑」变成门禁或检查清单。
  3. **指标**：更新「假失败率 / 卡死残留 / 开单→收口时长」，用于判断系统是否在变好。
- **门禁：不回写经验、无回归测试的 issue 不 close（见 `docs/agent-workflow.md` 四不 close）。**

## 2. 自强化 vs 自学习

| | 自学习 | 自强化开发 |
| --- | --- | --- |
| 产物 | 知识/经验 | 代码 + 测试 + 规则 + 指标 |
| 生效方式 | 被动回忆 | 主动进入下一轮门禁 |
| 可验证性 | 低（经验容易过期） | 高（测试红绿 + 指标趋势） |
| 失败模式 | 记住了但没变好 | 闭环某环断掉（最常见是 4 或 5） |

「自强化」的本质 = **环 5 的输出修正环 2/3/4 的门禁**。例如：

- 0.0.79 `ssh rc≠0` 假失败：环 4 实测暴露泄漏 → 环 5 回写「失败时读节点结果文件，绝不自作主张标 failed」，
  并把「失败 → 转 needs_manual 而不自动重传」写进检查清单 → 环 1 的巡检规则随之细化。
- 分 P 核验假 mismatch（T-32）：环 1 发现 13 个场次卡 `needs_manual` → 根因是上传成功
  后 0.5s 查 B 站列表未同步 → 环 5 回写「核验前等待最终一致 + 重查」，并加 `finalize-verify` 回归用例。
- 边录边传（#3）：环 1 磁盘写满 → 环 2 决策 → 环 3 实现中 → 完成后必须补「已封口分段
  上传确认后再删源」的不变量测试，并在环 5 把「低于水位拒绝新开录」沉淀为规则。

## 3. 闭环门禁清单（audit / triage / 实现 / review 各环对照）

开票前：
- [ ] 有命令输出（节点角色 + 时间）
- [ ] 过 `scripts/issue-guard.py`（正文与评论都过）
- [ ] 不夹带优化（优化单独开 `enhancement`）

决策后：
- [ ] 危险类 = `needs-decision` + 决定三行，等人回
- [ ] `accept` 才进 `TODO.md`（`T-N` + issue 链接）

实现与 PR：
- [ ] 一个 issue 一个分支，`Fixes #N`（分步票中间各步 `Part of #N`）
- [ ] 有回归测试（或写明人工验证步骤）
- [ ] 自审发现 → 修复清单可查
- [ ] PR 里说明评论哪些采纳 / 哪些不采纳及理由
- [ ] 自动认领前先打 `in-progress` + 留言「哪个 agent、何时开始」

自动化的边界（2026-10-12 起）：
- [ ] 自动 triage 只打标签，不写代码；危险类一律 `needs-decision`
- [ ] 自动实现只开 PR，不合并、不部署
- [ ] 自动 review 派独立会话只读审查，门禁全过即合并 PR，不部署
- [ ] 自动实现过「四不 close」后可自行 close issue，并写明关闭依据
- [ ] 并行最多 2 张 `in-progress`，且改动范围不重叠（避免多个会话互相打架）

发布与验证：
- [ ] 部署前 guard 0 在录（或用户 override）
- [ ] 核对版本号
- [ ] 实跑验证，有台账终态 + 文件系统证据
- [ ] 验证失败/未跑 = 如实写待办，不 close

关闭前（四不 close）：
- [ ] 无证据不开（环 1）
- [ ] 不验证不 close（环 4）
- [ ] 无回归测试不 close（环 3/5）
- [ ] 不回写经验不 close（环 5）

## 4. 指标口径（观察期手工统计，后续自动化）

| 指标 | 口径 | 目标 |
| --- | --- | --- |
| 假失败率 | `needs_manual` 中非真故障场次 / 当日收口场次 | 持续下降；0.0.79 修复后目标 < 5% |
| 卡死残留 | 节点 `recordings/` 中「台账 done 但源 .ts 仍在」的场次与字节 | 0 |
| 开单→收口时长 | issue 开票 → 合并后验证完成（自然小时） | 按严重度：P0 < 24h，P1 < 72h |
| 复发数 | 同一根因类 issue 在回写后的再次出现次数 | 0（新写法，防「好了又坏」） |
| 验证覆盖 | 修复类 issue 实跑验证比例 | 100%（无法实跑必须注明待办） |

统计来源：`sync_jobs` 台账 + 节点磁盘巡检 + GitHub issue 时间线。每个奇数日巡检把上周指标
追加到本文件「指标记录」小节（未做 = 记为缺口，不假装达标）。

自动化：`scripts/reinforce-metrics.py`（默认只读，`--write` 才落 `docs/metrics/<date>.md`）。
它聚合 `sync_jobs` 的 done / needs_manual / failed、疑似假失败率、master stage 卡死残留
（只读扫描，不删文件），并给出近 30 天已关闭 issue 的开单→收口平均时长。节点残留可加
`--node <host>`（同样只读）。用法：

```bash
python3 scripts/reinforce-metrics.py                      # 打印到 stdout
python3 scripts/reinforce-metrics.py --days 7 --write     # 写 docs/metrics/2026-10-12.md
python3 scripts/reinforce-metrics.py --node vps --node vps2
```

## 5. 边界与不做

- 不常驻四个 agent 互相派活；五环由 heartbeat / cron 承担：环 1 值班 Audit、环 2 自动 triage、
  环 3 自动实现（开 PR）+ 自动 review（审查通过即合并）、环 4 部署 guard、环 5 指标回写。
  不默认开一堆长驻 agent。
- 环 2 / 环 3 已自动化（2026-10-12）：`accept` 不再等人点名，自动 triage 出的 `accept` 会直接进
  实现流程开出 PR；**PR 由独立 review 会话审查，通过即自动合并**。人只负责**部署 / 危险类拍板**。
- 不碰线上行为：本文件只定义流程与门禁；具体修复仍走 issue → 分支 → PR → review 合并。
- issue 永不写隐私；编辑过的 issue 旧版本仍公开，第一版就要过闸门。
- 环 4 的「实跑一场」不是每次都必须全流程；但**收口类**（上传/删源/分P）必须有实跑证据或
  明确的待办，否则第 5 环无从回写。
