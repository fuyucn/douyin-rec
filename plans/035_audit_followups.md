## 2. 整改项

### F. 验证欠账（前置，不是新功能）
- `待验证` 的语义 = PR 已合并、**部署后线上实跑**再 close（`docs/agent-workflow.md`）。dev e2e（#82/#88）只能攒证据，**不能 close**。
- 顺序：部署（≥0.0.121，三节点无 `recording`）→ 线上按 #82/#88 清单实跑 → 逐条 close。
- 验收：27 个里每条有「证据评论 + close」或「缺口说明」。

### A. 失败证据剩余缺口（P0，纯诊断，无行为变化；依赖：部署 ≥0.0.109）
- `UserKnownHostsFile` 放持久目录，`StrictHostKeyChecking` 与 rsync 路径现有 `=no` **统一**口径（二选一，不要两套）。
- 节点结果文件的 `error` 作为独立字段落台账（现只拼进日志并 `slice(0,120)`）。
- `reconciler` 里仍 `slice(0,300)` 取头的三处改取尾。
- 验收：节点执行体中途抛错的用例，台账 `error` 含真实异常；不含 ssh 警告；容器重建后 known_hosts 仍在。

### B1. 「人工已处理」：改状态，不触发删源（P0）
- API + UI：对 `needs_manual` 的 job 填 BV → `done`、bv 落库、写事件；**不触发** `clean_*`，清理留给人工/既有规则。
- 队列页对超 24h 的 `needs_manual` 标红，并显示源占用（用清单 `totalBytes`；stage 字节若无数据源则先只显示源）。
- 验收：调用后 `done` + bv；重复调用幂等；不产生任何删除调用（用例断言）。

### B2. 填 BV 后是否算「确认」并触发清理（needs-decision）
- 冲突：033 I1 与 #92 的决定是「确认 = biliup rc=0」，人填的 BV 不是这个证据；034 §2.1 `confirm` 是唯一入口。
- 决定三行：要决定什么 = 人工填 BV 是否可触发删源；不做会怎样 = 人工补传后磁盘仍需手删；建议 = 不自动删，改为列出「可清理清单」由人一键确认。

### C. 上传线路按实测吞吐排序（needs-decision：改上传行为）
- 数据源 = #44 的「上传运行记录（线路、吞吐）」，不另建表；存库位置随 #44 定，`rankLines` 接入**所有**上传路径（边录边传、节点侧、master），不只一条。
- 证据缺口（先补再决定）：代码注释称选 alia 是因 txa 分块连接不稳 → 需要 txa 的换线/失败率数据，而不是单次样本。
- 真实试传须按 033 口径：**用户指定房间 + 仅自己可见 + 事后人工删稿**。
- 验收：`rankLines(history, defaults)` 纯函数单测；无历史时顺序不变（不改行为），有历史才排序。

### D. 超时按进度判死（挂 #25；依赖：A + #44）
- 现状：`字节/1MB/s + 20min`，封顶 6h。改成「N 分钟无字节增长才判死，6h 总上限兜底」。
- 注意：biliup 期间 ssh 本身无输出（ssh 传输模块已注明），所以字节读数要来自节点侧上传进度 = #44 的能力，这是真正前置。
- 验收：单测「N 分钟无增长 → 判死；持续增长 → 不判死；超 6h → 兜底」；dev 注入慢传验证不误杀。

### E. master 分段模式 pull 副本（在 #123 续做）
- 先量：dev 里同一场在 master 路径实际占几份；决策阈值 = 峰值磁盘 > 2× 场次体积 才做。
- 与 033 D4（默认不释放节点源）一致：只考虑去掉 master 侧 `.work`/重复 mp4，不动节点源。
