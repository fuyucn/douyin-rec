### A. 失败证据剩余缺口（P0，纯诊断，无行为变化；前置：无，0.0.120 已含 `d4c47dd`）
- **范围**：写入台账 `error` / `syncNodeState error` / `logStep` 的「取开头」截断点。已核实的位置：
  - 节点侧上传模块：`logStep` 的 `slice(0,120)`（2 处）、`note.slice(0,200)`（3 处，含 `setState needs_manual`）；
  - reconciler：`markFailed(...slice(0,300))` 与 `ok:false` 返回的 `slice(0,300)`（共 4 处）；
  - DAG 工作流：节点失败写 `syncNodeState error` 的 `slice(0,300)`（主要写入点之一）；
  - 整场/分段管线里同类点（`clean_stage` 失败等）：实现时 grep 全部 `slice(0, N)` 并逐个判断是否写台账。
  - 注意：节点结果 `error.slice(0,120)` 只进 `jlog`，**不写台账**，不在本项范围。
  实现时以 grep 结果为准，PR 里列出「已改 / 判定无需改」清单。
- 节点结果文件的 `error` 作为**独立字段**落台账——与 033 P3.0 的 reason 枚举合并设计，**不另造一套**；A 只负责「证据原文」，P3.0 负责「分类枚举」，两者字段分开。
- ssh 警告降噪：加 `-o LogLevel=ERROR`，**两处**都要加：ssh 直连调用与 rsync 的 `-e` 参数串（传输模块内两处），否则 rsync 路径警告仍在。不改信任策略，可安全做。
- 验收：节点执行体中途抛错的用例，台账 `error` 含真实异常尾部、不含 ssh 警告；对所有上述截断点各有断言；dev 构造一次真实失败并读台账。

### K. known_hosts 持久化与主机密钥策略（needs-decision）
- 作用范围：该配置**只对 `Host 100.* *.ts.net` 生效，且只在 master 镜像（`IMAGE_ROLE=master`）写入**，节点不受影响。
- 位置：Dockerfile 的 ssh 配置段（`StrictHostKeyChecking accept-new` + `UserKnownHostsFile /dev/null`）与 rsync 路径的 `StrictHostKeyChecking=no`。
- 决定三行：要决定什么 = 是否持久化 known_hosts 并统一两处口径；不做会怎样 = 每次连接都有警告（A 的降噪已使其不污染错误），无安全收益也无功能损失；建议 = 先不做，只有出现主机密钥变更/中间人场景需求时再做，并写明密钥变更后的恢复步骤。
- 验收（决策项）：决定三行评论齐备，你的选择落在评论里。

### B1. 「人工已处理」：改状态，不触发删源（P0；**第一步先核实，核实结果可能把它升为 needs-decision**）
- **第一步（读码+dev 实测）**：确认台账翻成 `done` 后，既有收尾补跑/`clean_verify`（见 #91）是否会触发清理。`hub recheck-verify` 的说明写着「源清理由既有 cleanup 路径处理」——若 `done` 确实会被补跑并删源，则 B1 与 recheck 一样**已沾上删源**，必须改为 needs-decision，不能走 accept。
- 方案：**扩展 `hub recheck-verify`**（它按 B站实查分 P 核验，证据强于人填 BV），增加「人工指定 BV」的入口；Web 只做调用与展示。不另起第二个翻 `done` 的实现（AGENTS.md：不要同一判定写两份）。
- **必须带可区分标记**（`manual` / `recheck` 来源，形式实现时定：列或事件字段）。034 的 `confirm` 只认 biliup 返回码 0；人工/重核 `done` 不等于确认。S4 `releaseSource`、容量账本的「done 但源残留」、`stageAfterDone`、补跑都据此标记处理：**不自动清理、不重新派发**。
- 队列页对超 24h 的 `needs_manual` 标红并显示源占用（用清单 `totalBytes`；stage 字节无数据源则先只显示源）。
- 验收：调用后 `done` + bv + 来源标记；重复调用幂等；**recheck 翻 `done` 与人工翻 `done` 两条路径下，下一轮对账都不派发、不删除**（用例断言无任何删除/上传调用）；非 `needs_manual` 状态拒绝。

### B2. 填 BV 后是否算「确认」并触发清理（needs-decision）
- 冲突：033 I1 与 #92 的决定是「确认 = biliup rc=0」，人填的 BV 不是这个证据；034 §2.1 `confirm` 是唯一入口。
- 现有语义：`recheck-verify` 已能按 B站实查分 P 翻 `done`，清理交给既有路径；B2 要决定的是这条既有路径对「非 biliup rc=0 确认的 done」是否允许删源。
- 决定三行：要决定什么 = 人工填 BV / recheck 翻 `done` 后是否可触发删源；不做会怎样 = 人工补传后磁盘仍需手删；建议 = 不自动删，改为列出「可清理清单」，由人一键确认。
- 验收（决策项）：决定三行评论齐备，你的选择落在评论里；选定后再据此开实现 issue。

### C. 上传线路按实测吞吐排序（needs-decision：改上传行为）
- 数据源 = #44 的「上传运行记录（线路、吞吐）」，不另建表；存库位置随 #44 定。**接入点只有一个汇合点**（线路候选函数 `uploadLineCandidates`，边录边传/节点侧/master 三处调用都经过它），在那里接 `rankLines`。
- **历史如何到节点**：节点侧上传在节点进程里跑 biliup，而 #44 的汇总在 master。须二选一并写进 issue：① master 把排好序的线路列表随节点管线 spec 下发；② 节点本地各自记录、各自排序。建议 ①（口径唯一）。
- 与 #23（504 换线，待验证）互相影响：排序会改变换线路径，须待 #23 线上验证后再做，或在验收里写明与换线逻辑的交互用例。
- 决定三行的**低代码备选**：环境变量 `BILIUP_UPLOAD_LINES` 能不改代码调整顺序（把 txa 提前），但要**逐节点改 env 并重启**，属于部署，受「无 `recording`」guard 约束，不是零成本。
- 证据缺口（先补再决定）：线路候选处的注释只说「探测可能选中延迟低但分块不稳的线路」，并未点名 txa；我们的实测是单次样本（alia 341 / bda2 1167 / txa 4437 KB/s），需要多次、多时段的换线/失败率数据才能推翻现有顺序。
- 真实试传须按 033 口径：**用户指定房间 + 仅自己可见 + 事后人工删稿**。
- 验收：`rankLines(history, defaults)` 纯函数单测；无历史时顺序不变，有历史才排序。

### D. 超时判死标准（新开 enhancement，needs-decision；前置：A + #44）
- 现状：`max(30 分钟, 字节/1MB/s + 20 分钟)`，封顶 6 小时（`estimateNodeUploadTimeoutMs`）。
- 提议：「N 分钟无字节增长才判死，6h 总上限兜底」。**这是新的上传行为语义**，所以 needs-decision，不挂 #25（#25 已 accept 的 ①② 已落地）。
- 进度来源要写清：biliup 运行期间 ssh 本身无输出（传输模块已注明），master 需要旁路读节点侧进度——来自 #44 的节点上传进度；#44 声明「只读观测」，D 把它用于判死即改变其性质，须在 D 的 issue 里写明并同意。
- 决定三行：要决定什么 = 超时是否改按进度判；不做会怎样 = 慢线路上大场次仍可能被总时长杀；建议 = 先做 C（线路选对）再评估 D 是否还有必要。
- 验收：单测「N 分钟无增长 → 判死；持续增长 → 不判死；超 6h → 兜底」；dev 注入慢传验证不误杀。

### E. master 分段模式 pull 副本（新开小 issue，链 #123）
- #123 标签：`accept → 待验证` **不是合法迁移**（`docs/agent-workflow.md`：须经 in-progress → in-review → PASS，或由 review 心跳在合并时转）。#124 合并时漏了这一步，属流程缺口，计划里记下；处理方式 = 补走合法路径或由 review 心跳补转，不手改标签绕过脚本。
- 在新 issue 里登记 master 分段模式的剩余范围，并链到 #123。
- 先量：dev 里同一场在 master 路径实际占几份；决策阈值 = 峰值磁盘 > 2× 场次体积 才做。
- 与 033 D4（默认不释放节点源）一致：只考虑去掉 master 侧 `.work`/重复 mp4，不动节点源。
- 验收：dev 实测报告（各阶段峰值磁盘 / 场次体积）落在 issue 评论；低于阈值则 close 为「不做」并写依据。
