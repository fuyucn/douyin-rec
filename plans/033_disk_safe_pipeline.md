## Goal

无人值守下，磁盘空间不靠人去清、不靠删除未确认的录像、不靠打断录制来保证，而靠流水线每一步都**正确且及时**：

1. 上传的每一步结果可证明（不依赖 ssh 会话与回读的偶然性）；
2. 源文件在**该分片已确认**后立即释放，不等整场、整条流水线；
3. 失败按类别处理：该自动重试的自动重试，其余才转人工，且转人工的原因可分类、可统计；
4. 边录边传成为「具备条件」房间的默认形态，节点上的占用有可计算的上界；
5. 需要后处理的房间（多节点、烧录）保留并 pull 到 master 处理，占用由容量账本可见、可预测。

**诚实的边界**：在「I1 不删未确认录像」与「I2 不打断录制」同时成立时，「磁盘不满」只在**被 I1 锁定的字节不超过预算**时成立（见「容量预算」）。超出预算意味着确实需要人决定取舍，本计划的目标是把这种情形压到最少并提前、明确地暴露，而不是承诺它永不发生。**超预算时系统的自动行为是「在新一场开播处拒录」（即丢新内容，而不是删旧录像、也不是打断正在录的场）**，这一点明写；同时规定**优先级：后处理（remux、pull）的准入必须给录制留出余量，后处理永远不能把录制挤到闸门以下。**

## Architecture

### P0 验证基础设施（先于其它实现）

dev 集群目前无法验证本计划的大部分行为：mirror 档强制 `stage` 模式、假 biliup 无故障注入、internal 档回读恒为空、没有写满磁盘与重启接管的手段。P0 补齐：假 biliup 故障注入（超时 / 非 0 / 限流 601 / 慢传 / 响应丢失）、带延迟的回读替身、容量受限的卷（写满 ENOSPC）、假流源（可控闪断 / 立即失败）、节点执行体存活与 ssh 断开的注入。**P1 之后的每步验收都以 P0 为前提。**

### P1 让「上传每一步正确」可证明

- **P1.1 节点执行体自治，拆为 5 个独立 PR**：
  1. #25 ②：建稿拿到 BV 后立即落盘、每次追加成功后立即落盘；**追加前先写「意图」**（`intent(i)`），重入时若 `intent > 已确认序号` 按 I3 ② 处理（阻塞式间隔重读，读不出则转人工）——否则在「返回码 0 → 落盘」之间被终止时，重入序号偏低会重复追加。**重入以落盘的确认序号决定续传位置，不再靠单次回读**（现状节点重入只回读一次分 P 数，违反 I3 ②）。落盘阶段本身（`started → uploading → done|failed`）已存在，缺的是这一点。
  2. #25 ①：超时按字节估算，取代固定 30 分钟。
  3. 落盘结果回读改为**四态**：存在（读自执行体按 spec 落盘的路径）/ 不存在（且该路径所在 stage 子目录确实存在）/ 损坏 / 不可确定（节点不可达、stage 目录不存在、读取路径与落盘路径可能不一致）。
  4. 执行体脱离 ssh 运行，带能力协商；提供**不杀进程的存活探测**。旧 bundle 降级为现状。
  5. **master 重新挂接（租约方案，取代 v2 的「启动时不清扫」）**：每轮 reconcile 开头都会做 stale 清扫（不是仅启动时；默认阈值约 10 分钟），而 reconcile 受并发守卫、对账间隔约 30 分钟，脱离 ssh 的执行体若不被「流锁」保护，会被标成「进程重启中断」并转人工。因此：
     - ① **租约由守卫之外的独立定时器续期**（不在 reconcile 内），把「流活跃」判定改为「持有流锁 **或** 租约新鲜」；
     - ② **只凭节点存活证据续期**（如节点上执行体 cmdline 校验通过 + 结果文件推进），不得由 master 自行续期，否则已死的执行体会被永久续租、job 永不被清扫（静默卡死）；
     - ③ 续期用**专用的 touch**，不能复用状态写入（它每次让尝试次数 +1，会让 UI 的尝试次数失真）；
     - ④ master 启动时、第一轮 reconcile 之前，按处于「节点侧上传中」的状态行重新挂接；
     - ⑤ 节点用独占 pid 文件拒绝重入时，**必须返回可区分的 busy**：现网拒绝表现为进程非 0 退出、传输层只带错误尾部丢弃标准输出，会被当成失败并触发终止命令——需要独立的退出码或 stderr 标记，且 busy 判定与终止命令一样用 cmdline 校验（只用 `kill(pid,0)` 会在 pid 被回收时误报永久 busy）；master 收到 busy **不得**调用终止命令。
     - ⑥ 部署顺序逐步骤写明：新节点兼容旧 master（不返回 busy 则按现状）；busy 只能由新 master 消费，故 P1.1e 要求**节点先于 master**。
- **P1.2 失败分类（先观察、后启用）**：
  - **P1.2a 观察版**：纯函数 + 表驱动测试，只**记录**「本会如何处置」，不改变行为，积累真实分布。
  - **P1.2b 启用自动重试**，仅限下表标「自动重试」的行：
  | 回读结果 | 执行体 | 处置 |
  |---|---|---|
  | `started` | 已确认终止 | 自动重试（次数上限） |
  | 不存在（读取路径 = 落盘路径，且 stage 子目录存在） | 无 pid、已确认不存活（需 P1.1d） | 自动重试 |
  | `started` / 不存在 / 不可确定 | 未知或无法探测 | 等待并重读；超时转人工 |
  | `uploading` | 存活（需 P1.1d） | 继续等待，不转人工（上限后转人工） |
  | `uploading` | 已死 | 转人工（建稿可能已发生，I3 ①） |
  | `done` ∧ `ok` ∧ BV | — | 成功（I1） |
  | `failed` 且有 BV | — | 转人工，保留源（I3） |
  现状「确认没成」分支同时标 `upload_plain` failed，使可重试情形也被当不安全重试转人工；拆开时**只放开表中明确标「自动重试」的行**。节点执行体建稿前失败是有意写 `uploading` 而非 `failed` 的，不得改成可重试。含「存活 / 已死」的行依赖 P1.1d，在其落地前一律按保守处理。
- **P1.3 分片状态机 = #72 的清单 v3（节点侧）+ master 镜像，不另起第二份台账**：本计划的抽象状态 `pending → uploading → confirmed → released` 与 #72 的 `open / sealed / uploading / acked / sourceDeleted / ambiguous / needs_manual / skipped` 对照为 `open,sealed→pending`、`uploading→uploading`、`acked→confirmed`、`sourceDeleted→released`；**#72 允许「回读证实已提交」把分片推进到 acked（进而 sourceDeleted），这违反 I1 / D8，须在 P2.1a 中改为 `ambiguous`（保留源）**。`released` 只允许从 `confirmed` 进入；幂等键 `(streamKey, sessionBase, partIndex)`；崩溃恢复以清单与台账为准而非文件存在性。这使 P1.3 与 P2.1a 合并为同一条线，并要求先解除 #72 的竞态。**危险类，需人确认。**
- **P1.4 磁盘写满与无效分段**：
  - **P1.4a 调查** 0 字节分段的根因（ENOSPC 还是真闪断）。
  - **P1.4b 水位闸门补全（核心，不删任何文件），拆为两步**：
    - **a（不含重连）**：录制子进程在「新一场开播」处按水位拦截；手动启动接口也过同一闸门。实现要点：「新一场」与「同场重连」在录制引擎里不可区分（二者都走同一轮询起录制），只有会话层的「仍在直播」标志知道，需由会话层把该标志传下去；子进程应测**任务自己的输出目录**所在卷（现有统计测的是默认输出目录）；水位值要**运行时可更新**（常驻进程不能只在启动时固定）。这一步不碰上传与删除，**可单独上线**，直接堵住写满盘的主通路。
    - **b（同场重连硬下限）**：仅当本会话已观察到 ENOSPC，或剩余低于约 1GB 时，才拒绝同场重连；空间恢复后自动继续轮询并告警。这是对 I2 的受控例外，**依赖 D6**。
  - **P1.4c 后处理跳过无效分段**（0 字节 / 探测失败）并记录，不拖垮整场。v2 的「会话结束清理 0 字节输出」**取消**：0 字节文件不占数据块，删了腾不出空间，却要碰 `recordings/` 删除。

  - **占用上界与稳定性条件**：上界 `= Σ_房间[ 一段 + R_i·(封口延迟 + 单段上传耗时) ] + max(0, ΣR − U_eff)·T_live + 降级积压`，其中 R_i 为单房间码率、ΣR 为节点上同时在录房间码率之和、U_eff 为该节点**实测**有效上传吞吐（上传按账号串行，并受 601 冷却影响）。公式只在 `ΣR ≤ U_eff` 时给出有界结果；默认化门槛设为 `节点 ΣR_peak < 0.8·U_eff`，U_eff 由容量账本实测（现有实测：单文件约 0.7MB/s 端到端，一个节点约 2–3 个并发房间就会开始积压）。
- **P2.3 后处理房间节点源提前释放（独立决策轨道，默认不实施）**：「pull 副本校验后释放节点源」与 I1 / `plans/031` 不变量 3 冲突，须先由用户决定 D4。若批准，须同时：① 重试入口从「依赖节点清单」改为「依赖台账 + stage」（否则无 ts 的场次会从清单里消失，无人推进）；② 排除「master 本机胜出（stage 为硬链接，释放不腾空间）」的情形；③ 写明落败节点副本的处理；④ 校验强度由 D2 定。未批准时，后处理房间的占用由 P3 的容量账本与背压管理，不提前释放。

## 容量预算（目标成立的条件）

- **节点侧上传的峰值**：约 `源 + .work（≈ 同量级）`，即约 2 倍场次大小；现有闸门只检查剩余 ≥ 10GB，remux 中途仍可能 ENOSPC（031 记录的那次事故）。→ I12：remux 准入要求 `剩余 ≥ Σ分段大小 × 1.1 + 预留`，不足则带原因延后，**且不回落 pull 到同样放不下的 master**；P3.5 做完后峰值回到「一段」量级。
- **master 的汇聚预算**（同一个卷上）：`本机 worker 录制预测 + 在途 pull × k（烧录房间 stage 峰值约为场次大小的 3–4 倍）+ 被 I1 锁定的 needs_manual 字节 + stage 模式长期保留 + 日志与镜像`。当前 master 在 90% 以上，pull 前**没有磁盘准入**（只检查内存）——必须由 I12 补上。
- **容量账本需单列的类别**（本轮审计补）：「`done` 但源残留」（含旧版遗留 `clean_verify=pending` 场次，这些源需人工清理）、「规则未开启清理（`cleanup.sourceAfterDone` 关）导致源永不删」、「回读判定已提交但不算确认（D8）」。
- **I1 锁定的字节**：`needs_manual` 场整场无保留期，只增不减。P1.2b 与 P3.0 的目标就是让它**不增**；已存在的则由容量账本显示并提示人处理（本计划不替人删）。
- **验收口径**：灰度与上线以「峰值占用 ≤ 公式上界」「锁定字节趋势不增」「无因磁盘导致的 0 字节分段」判定，而不是「永不满」。

## Global Constraints

- 基线 `feat/hub-optimization`；禁止向 `main` 提交、开 PR 或合并。
- 每步一个 PR，可单独回滚；DB 列保留，读取时迁移，不做破坏性迁移；新字段旧节点包可忽略。
- **开关策略**：现有「实验性」注册表只驱动徽标、不参与行为判定，不能当开关用。因此：① **纯安全性改动免开关**（P1.1a 立即落盘、P1.1c 多态回读、P1.4b/c、P3.0）；② 节点侧新行为（P1.1d 等）靠**能力协商**控制，旧节点自动降级，不在 master 上加全局开关；③ master 侧改变处置的步骤（P1.2b、P2.2a、P3.2）在 hub 配置 / 规则里加**显式具名开关、默认关**，每个 PR 写明键名与所在位置；回滚靠关开关。
- **部署顺序**：以能力协商为准——新节点兼容旧 master，新 master 对旧节点降级，故顺序不敏感；推荐**节点先、master 后**。#57 写的「主控先」指 rolling 清单的读取，两者以各步骤的能力协商为准。灰度的前提是 #92 / #91 / #89 **已部署**：master 与两个 VPS 节点的 `/api/version` 均为 `0.0.105-45ecab`（2026-10-14 部署后取证），仍待实跑验证。
- 涉及上传 / 删源 / 清理判定的步骤合并前须人确认（风险扫描命中即停）；部署由人做，部署前全节点 `recording !== true` 且磁盘预检通过。
- 每步过验证门：`pnpm test`（看退出码与未处理异常）、`pnpm typecheck`、`pnpm bundle`；动前端加 `cd packages/web && pnpm build`；动运行时在 dev 集群实跑并留台账、文件、API 三路证据；行为变更须回归测试并做变异验证。
- 文档与 issue 过 `python3 scripts/issue-guard.py`。
