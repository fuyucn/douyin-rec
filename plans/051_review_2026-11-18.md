# plans/051 设计评审（2026-11-18）

> 评审对象：[051_pipeline_step_registry.md](051_pipeline_step_registry.md)（状态：设计待评审）。
> 结论：**方向成立，但不能按现稿直接进 P1；先补四项契约与一个对拍基线，再拆阶段。**

## 结论摘要

计划想解决的三件事都真实存在：步骤词表一份、执行写法五份、拓扑两份。把执行器下沉到低层包、
让步骤成为数据，是正确方向。现稿的主要问题不是“要不要做”，而是**用一个 DAG 执行器同时吞掉
合并、分段、节点三种语义差异很大的写法**；其中分段模式不是单张 DAG，而是“每组循环 + 组内追 P”。
如果不先把这层建模清楚，P3 会把状态机搬成一个更复杂的图，而不是删掉它。

建议把首刀缩小为“**纯数据注册表 + 合并模式对拍**”，执行器下沉与分段/节点接入分阶段做，
每阶段都有可回退的行为对拍。

## 必须修正的发现

### P1-1 分段模式不是单张 DAG

`packages/orchestrator/src/segment-pipeline.ts` 的状态机按“组”循环：每组 remux、合并、建稿、
逐段 append、核验、清理，组与组之间共享会话但状态独立。计划 §6 把“一批 N 段”留在 `merge` 的
run 里，图里只保留一个 `upload_plain`/`append_*`，这无法表达：

- 每组一个稿件、逐组追 P；
- 组失败只影响该组，不阻塞其他组；
- 每组的 `clean_stage_src`/`clean_verify` 时序；
- 续跑时“哪些组已完成、哪些段待补”。

P3 必须先选一种模型：(a) 一组一张小图，循环由外层驱动；(b) 保留分段状态机，只共享
`StepSpec` 元数据与 UI 拓扑，不强行接执行器。**在选定前，P3 不应开工。**

### P1-2 执行器下沉的依赖边界没有落地

`runWorkflowNodes` 的 `NodeRunContext.deps` 是 `PipelineDeps`，包含 `Transport`、`SyncLedger`、
`UploadTarget`、资源池、logger、`countParts`、`splitForUpload` 等 20 多个字段，且多数类型定义在
orchestrator。计划说把执行器搬到 `@drec/pipeline`（rank 0.6，只依赖 core），但没有说明
`PipelineDeps` 是搬走、复制还是改成结构化 port。

直接搬会把 orchestrator 的类型拖进低层包；复制会制造第二份接口。建议：

- pipeline 只定义 `StepContext` 的**结构化最小面**（artifacts、log、sh、ledgerPort、resourcePort、
  uploadPort、config snapshot），不 import orchestrator 类型；
- orchestrator 保留 `PipelineDeps` 装配与适配器，把闭包传给 `runGraph`；
- 先做一张“字段 → 谁提供 → 是否可空”的清单，再决定哪些字段进 `StepContext`。

### P1-3 上传驱动的依赖方向互相矛盾

计划要求 `upload_plain`/`append_*` 只调 `UploadDriver`，同时要求 `@drec/pipeline` 不依赖
`@drec/upload-runtime`。`UploadDriver` 目前定义在 upload-runtime，`StepSpec.run` 若直接引用它就会
反向依赖。§10.1 只把问题留成未决项，不能带进 P4。

建议在 pipeline/core 定义**最小上传 port**（`ensureArchive` / `appendParts` / `verify` 的结构签名，
不 import 实现），由 upload-runtime 或组合根适配；驱动仍只在调用方注入。这样 P4 的行为对拍
可以独立于包边界。

### P2-1 步骤数量写错

`packages/core/src/hub-ledger-contract.ts` 的 `HUB_STEP_NAMES` 是 **13 个**，不是计划多处写的 14 个：
`select / pull / node_upload / merge / burn_danmu / burn_livechat / upload_plain / append_danmu /
append_livechat / clean_verify / clean_stage_src / clean_source / clean_stage`。
注册表、对拍和验收计数都要按 13 修正，否则 P1 的“节点/边完全一致”断言一开始就是错的。

### P2-2 “加步骤 = 表里一行 + 图里一条边”不成立

`HUB_STEP_NAMES` 是 UI/旧库外部契约，新增步骤仍要改 core 词表、web 文案/映射，计划 §4.1 也承认
“这是有意的摩擦”。目标应改成“**五种执行写法收敛为一张表；加步骤仍要改词表与 UI 映射**”，
不要把摩擦藏起来。否则评审会误以为可以无成本扩展。

### P2-3 `select` / `pull` 不是执行器节点

合并模式的 `select` 在 reconciler 里完成，`pull` 是图外前奏（`workflow.ts` 顶部注释明确写了）。
把它们塞进图里当占位步骤，会让“图 = 实际执行序列”失真，也会迫使 reconciler 的状态机改接口。
建议：图从 `pull` 之后开始；`select` 只作为 UI/台账的边界事件记录，或由调用方在 `runGraph`
之前显式执行。§10.2 应直接定为“不进执行器”。

### P2-4 清理步骤的失败语义没有定

`clean_source` 是不可逆删除；现有实现把清理失败记到 `recordCleanFailure`，由 reconciler 补跑，
而不是让整场上传失败回滚。计划 §10.3 仍把它留成问题。建议明确：清理是**上传/核验成功后的
后置副作用**，图里只允许 done/skipped；失败不把已成功的上传改为 failed，只保留补跑与告警。
否则“图执行器统一失败语义”会改变删除策略。

## 对 §10 未决问题的建议回答

1. **pipeline 与 upload-runtime 边界**：pipeline 定义最小上传 port，不依赖 upload-runtime；
   upload-runtime 实现适配，组合根注入。与 `UploadTarget` 的注入方式一致。
2. **select 入图**：不进执行器；留在 reconciler，图从 pull 开始。若 UI 需要，记录为边界事件。
3. **clean_* 入图**：保留为后置副作用；图里标 done/skipped，失败走既有 `recordCleanFailure` 补跑，
   不转正常步骤 failed。
4. **分段模式**：先选“一组一图 + 外层循环”，还是“保留状态机、只共享元数据”；在 P3 设计评审中
   用真实 `test/e2e/segments.test.ts` 对拍后再定。不要先按一张大图实现。

## 修订后的阶段建议

| 阶段 | 内容 | 行为变化 | 退出条件 |
|---|---|---|---|
| P0（新增） | 冻结现有三模式行为；建立 execution-trace 对拍夹具（步骤状态、事件、skipped、detail）；盘点 `PipelineDeps` 字段 | 无 | 同一批 fixture 在旧实现上产出稳定 trace |
| P1 | 只提取 `StepSpec` 元数据与图数据；合并模式仍用原执行器；`hub-flow` 由同一数据生成或对拍 | 无 | nodes/edges **及 trace** 与旧 `buildWorkflow` 一致；13 步计数正确 |
| P2 | 合并 + 节点模式接入同一执行器（节点侧先做适配）；分段暂不接 | 无 | merge/node 用例与 trace 对拍绿；app 不再复制执行器 |
| P3 | 分段模式：按选定模型（组子图或保留状态机）接入 | 无（对拍） | `test/e2e/segments.test.ts` + 真实 trace 绿 |
| P4 | 上传步骤改走最小 port → 驱动 | 有（失败分类更保守） | plans/049 2b 实机验证；五条路径收敛 |

P4 仍单独评审。P0/P1 可以合成一个 PR，但必须先把对拍夹具写出来；否则“纯搬迁”没有可证伪的
退出条件。

## 其他风险

- **生成物回环**：计划让 `scripts/gen-hub-flow.mjs` 读 pipeline 注册表并写 core 常量。core 是 rank 0，
  pipeline 依赖 core；构建/typecheck 顺序与生成物新鲜度需要明确（生成脚本进 CI，漂移测试红）。
  更简单的替代是：把纯图数据放 core，pipeline 读它；执行器只消费图，不反向生成 core。
- **条件边**：`append_danmu → append_livechat` 在执行侧是条件边，展示侧无条件收录；改成生成物后
  必须保留“展示图”和“执行图”的差异，不要让 UI 图假装执行顺序。
- **失败重试**：`autoRetry` 只是声明，P1 不生效；若 P4 要按步骤重试，必须先把“失败分类”
  （限流/不确定/不可逆）映射到每个步骤，不能只靠布尔值。
- **层守护**：新增 `@drec/pipeline` rank 0.6 后，orchestrator/app 的依赖方向要加 arch 测试；
  否则未来又会有人把 orchestrator 类型拖进去。

## 建议的下一步

2. 把本评审的 P1 结论写回 `plans/051` 的 §10，确定 `select`/`clean_*`/分段模型。
3. 再开 P1 的纯数据注册表 PR；不要同时动执行器、hub-flow 和上传。
