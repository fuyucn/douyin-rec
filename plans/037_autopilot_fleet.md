# 037 全自动流水线 + fleet 式房间管理

> **TODO：T-61**（`TODO.md`「待办（Next）」）。基线 `feat/hub-optimization` = `5692c98`（含 #185）。
> 前置：plan 033（磁盘安全不变量 I1–I12）、plan 034（交付模型）、plan 036（Processor 契约）不变。

状态：设计稿。本计划只定「什么该自动、什么该藏起来、什么必须人看」，不改选优/对账/上传语义。

## Goal

把 app 从「三个页面各自管一摊」变成**一条默认全自动的流水线**：监听 → 录制 → 投稿，
人只在**新增房间 / 改录制要求 / 看日志 / 处理极少数红灯**时出现。

用户口径（2026-10-16 会话确认）：

- **主流程只有三段**：监听直播间 → 录制 → 上传投稿。烧弹幕、存档（stage）、多格式输出都是**增强开关**，默认关。
- **不备份**是常态；archive 只在显式开启时发生，关闭时源文件按投稿确认后删。
- 目标是像 **biliup fleet** 一样：房间自己跑，人看的是「健康度」，不是「操作台」。

## 1. 现状实测（2026-10-16，master 7860）

- 17 个房间 / 17 条 hub 规则 / 17 个 task —— **三者一一对应**，拆成「任务页 + hub 房间页」在用户侧没有信息增量。
- 15/17 房间配置**完全同构**：全天窗口、单节点、投稿模式、公开、不烧弹幕、清理全开、按分段。
- 近 28 场 `needs_manual` **20 场（~70%）**，分类：

| 类别 | 场次 | 性质 |
|---|---|---|
| 边录边传分 P 未核实 | 7 | 增强功能，不开则不产生 |
| 节点侧上传 SSH 失败 | 6 | 真故障，应自愈或重试 |
| 边录边传建稿结果未知 | 3 | 同上，且已禁自动重试 |
| ffmpeg 失败 | 1 | 真故障 |
| 重启接管失败 | 1 | 真故障 |
| 空 error（`waiting_upload`） | 2 | **不是故障**，是 stage 模式房间（只存档不投稿）正常收口被塞进人工收件箱 |

→ **结论：人工收件箱里 ~2/3 是增强功能与配置口径造成的噪音，不是需要人救的火。**

## 2. 设计

### 2.1 一个首页：`/rooms`

房间列表即 app 首页。每行一屏读完：**在录 / 等待开播 / 今日已录多久 / 上次投稿结果 / 红灯计数**。
进详情 = 任务详情 + 规则编辑 + 内联日志尾巴（SSE）。

`/tasks` `/hub` `/queue` 全部收进「高级」导航折叠区，**不删、不改路由**，随时可回。

### 2.2 配置模板（替代逐房间配置）

17 个房间里 15 个配置一样，但今天要改 15 次。引入模板：

- 模板 = `pipeline` + `窗口` + `节点策略` + `清理` 的一组默认值。
- 房间只存 `templateId` + 少量 override（房间 URL、是否烧弹幕、输出格式）。
- 「改录制要求」= 改模板一次 → 所有引用房间生效（写回 `hub/{platform}.{room}.json`，保持**文件仍是唯一真理源**）。
- UI 上表现为「应用到 N 个房间」，执行后按房间逐条落文件 + 汇总结果，不做批量事务（配置文件无事务模型，半写失败比整体失败更难排查）。

### 2.3 fleet 式节点分配

现状：分到哪个节点是人手选的。新增房间时**自动选**：

- 打分维度：在线 / 磁盘余量 / 当前并发录制数 / 平台 cookie 可用性。
- **只对新增房间生效**；已在录的房间**绝不自动迁移**（重复投稿风险，见 #148/#177 同类事故）。
- 允许人工覆写，覆写值持久化，不被下次自动选覆盖。

### 2.4 人工收件箱只留真事故

- 增强功能（边录边传 / 存档 / 烧录）失败 → 归到「增强」分组，不占首屏红灯。
- `waiting_upload`（stage 模式正常收口）→ 移出 `needs_manual`，改标 `archived`。
- 真故障（SSH 上传失败、ffmpeg 失败、重启接管失败）→ 红灯，且必须**自带重试按钮 + 失败原因 + 直达该场日志**。
- 通知/webhook 必须带主播名 + 北京时间日期（#183 已落地），继续沿用。

### 2.5 自愈优先于告警

顺序：**先让 job 自己能收敛，再考虑通知人**。

1. 上传 SSH 失败 → 在节点侧重试（复用已有重试预算），用尽才转人工。
2. 重启接管失败 → 下轮 reconcile 自然重试，不立即转人工。
3. 边录边传分 P 未核实 → 后台延迟回读（#66 已有前置），回读仍不确定才转人工。
4. 任何 `needs_manual` 必须有非空 `error`（空 = 代码缺陷，违反 AGENTS.md「不静默」）。

## 3. 拆票顺序（低风险先行，高风险各自单独放行）

| 步 | 内容 | 风险 | PR |
|---|---|---|---|
| 1 | `waiting_upload` 移出人工收件箱 + 空 error 兜底为显式原因 | 低 | 本计划首个 PR |
| 2 | 通知/webhook 补该场直链；人工收件箱分组（真事故 vs 增强） | 低 | |
| 3 | `/rooms` 首页化 + 内联日志 + 任务/Hub/队列收进「高级」 | 中（纯前端） | |
| 4 | 配置模板 | 中（写回口径） | |
| 5 | 节点自动分配（仅新增房间） | 高（重复投稿风险） | 需人工放行 |

每步独立 issue → 分支 `codex/issue-<N>-<slug>` → PR → review 会话 → `needs-decision` 判定后合。

## Global Constraints

- 配置文件仍是唯一真理源，UI 不缓存规则（沿用现状）。
- 不删任何源录像；清理只由显式开关驱动（plan 033 I1–I12）。
- 默认口径必须是「录完就投、投完就删」；存档/烧录/多格式全部默认关。
- 模板批量写回不做事务，逐房间结果必须可见。
- 已在录的房间永不自动迁移节点。
